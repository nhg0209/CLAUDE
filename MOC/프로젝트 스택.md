# 프로젝트 스택 정리

현재 진행 중인 **RL 기반 E2E 자율주행 레이싱** 프로젝트의 스택 전체 지도.
학습 로드맵은 [`docs/RL_ROADMAP.md`](../docs/RL_ROADMAP.md), 논문 계보는 [[RL 지도]].

> [!abstract] 한 줄
> 팀이 이미 구축한 **classical map-based 스택**(Localization → Global Planning → Local Planning → Control)을,
> **TM07식 Asymmetric SAC 기반 E2E policy**로 대체하는 것이 목표. 센서·차량·시뮬레이터 계층은 그대로 재사용한다.

## 1. 전체 구조

```mermaid
graph LR
    subgraph HW["하드웨어 (공통)"]
        L[LiDAR] --> C[Jetson]
        I[VESC IMU] --> C
        C --> V[VESC ESC/서보]
    end
    subgraph ASIS["AS-IS: Classical (구축 완료)"]
        C -.-> LOC[Localization<br/>Cartographer / PF] --> GP[Global Planning<br/>TUM optimizer] --> LP[Local Planning<br/>trailing] --> CT[Control<br/>PP + friction circle + PID]
    end
    subgraph TOBE["TO-BE: RL E2E (목표)"]
        C -.-> POL[Policy Network<br/>Asymmetric SAC] --> DRV[/drive]
    end
    CT --> V
    DRV --> V
```

**핵심 전환**: `Localization → Planning → Control` 파이프라인 **전체**를 하나의 신경망이 대체합니다.
Localization은 policy에는 불필요하지만 **lap counting·평가·안전장치용으로 남습니다.**

| IMU | VESC 내장 | ⚠️ 차체 기준 **yaw +90° 장착** → `vesc_imu_rot`(−90°)으로 보정 |

### TF 트리 (실차)

```
map
└─ (cartographer 또는 EKF) → base_link
   ├─ laser        (x=+0.27, z=+0.11)
   └─ vesc_imu     (yaw=+90°)
      └─ vesc_imu_rot (yaw=-90°)   ← cartographer tracking_frame
```

> [!warning] IMU 장착 오차
> `vesc_imu_rot`이 두 번 회전하는 이유는 IMU가 물리적으로 90° 틀어져 장착됐기 때문입니다.
> **RL 관측에 IMU를 넣는다면 이 보정을 시뮬과 실차에서 동일하게** 적용해야 합니다.

## 4. AS-IS — 팀이 구축한 Classical 스택

> [!info] 출처
> 노션 「자율주행차만들기 수업: 회의 & 코드 허브」의 *최종 스택 정리* 및 *Creating_autonomous_car 스택 설명*.
> **여기 기록된 실패 사례가 RL 전환에서 가장 값진 자산**입니다. 같은 물리적 한계를 다시 만나기 때문입니다.

### 4-1. Localization

**구성**: Cartographer(2D SLAM) 또는 Particle Filter → EKF가 위치 + VESC 속도 융합 → `/car_state/odom`

3가지 모드로 분기: `gt`(시뮬 전용) / `cartographer`(메인) / `pf`

| 겪은 문제 | 원인 | 해결 |
|---|---|---|
| mapping 품질 저하 | loop closure가 **평행한 두 직선 구간을 하나로 통합** (parallel corridor aliasing) | `mapping_2d.lua` 파라미터 튜닝 |
| 직선 급가속 시 localization 터짐 | 스캔 데이터가 밀림 | **Particle Filter로 전환** → 고속·급회전에서도 안정 |
| 출발 시 뚝뚝 끊김 | 가속도 제한으로 초기 속도가 `0.04`로 들어감 | 정지→출발 시 속도 `0.5` 부여 |

주요 파일: `mapping_2d.lua`, `localization_2d.lua`, `pf.yaml`, `particle_filter.py`, `ekf_pf.yaml`

**주요 토픽**: `/scan`, `/vesc/odom`, `/tracked_pose`, `/car_state/odom`

> [!tip] RL 전환 시
> E2E policy 자체는 localization이 필요 없습니다(raw LiDAR를 직접 먹음).
> 하지만 **`r_progress` 계산, lap counting, curriculum 전이 판정, 평가**에는 여전히 필요합니다.
> 고속에서 검증된 **PF를 유지**하는 것이 안전합니다.

### 4-2. Global Planning

**구성**: TUM `global_racetrajectory_optimization` 기반 optimizer → centerline 추출 → 속도 프로파일 생성

| 겪은 문제 | 해결 |
|---|---|
| 코너 커팅, 경로가 벽과 거의 겹침 | **GIMP로 `.png` 맵 이미지를 직접 수정**해 원하는 경로 유도 |
| 속도 프로파일용 차량 물리 파라미터 부재 | **직접 측정 스크립트 작성** (`friction_test.py`) |
| 컨트롤러 튜닝 편의 | `waypoint_publisher.py`에 `speed_scaling` 파라미터 추가 |

맵 자산: `hall_0602`, `hall_0611` (`.pgm` / `.png` / `.yaml`, `hall_0611_modi2.png`)

> [!important] 로드맵 리스크 1순위와 직결
> 로드맵은 "**1/8 Serpent 차량 파라미터 미확보**"를 최대 리스크로 지목합니다.
> 그런데 이 팀은 이미 `friction_test.py`로 **마찰·가속도 한계를 실측**했습니다.
> → **그 측정값을 그대로 f1tenth_gym 파라미터로 옮길 수 있는지 먼저 확인**하세요.
> 사실이라면 M0~M1의 최대 리스크가 상당 부분 해소됩니다.
> (단 4-3의 기록상 "실측값이 정확하지 않았다"고 되어 있어, **재측정이 필요할 수 있습니다.**)

### 4-3. Control

**구성**: Pure Pursuit + **friction circle** + heading PID

동작 방식:
1. 코너 곡률과 차량 가속도로 **현재 횡가속도** 계산
2. 최대 횡가속도를 넘지 않는 선에서 **횡·종 가속도 배분**
3. 배분된 가속도를 **steering 보정값 + 종방향 속도**로 변환
4. 남는 heading error를 **PID**로 제거

| 겪은 문제 | 원인 |
|---|---|
| 고속 코너에서 언더/오버스티어, 지속적 헤딩 오차 | **실측한 횡·종가속도 한계값이 부정확** |

**튜닝 순서** (경험적으로 확립된 순서 — 그대로 기록):
1. 직선 급가속에서 경로 유지되는 **최대 lookahead**
2. 직선→헤어핀 진입 감속 시 덜 흔들리는 **`k_ff`**
3. 전 구간 돌며 적절한 **`k_v`**
4. 고속 코너에서 바깥으로 안 밀리도록 **K, D 게인** (**I = 0**)
5. 가속도 한계를 올리고 → 1번부터 반복

주요 파일: `pp_heading_controller.py`, `pp_heading.yaml`, `pp_heading.launch.xml`

> [!tip] RL 전환 시
> 이 Pure Pursuit 컨트롤러가 **Phase 2의 opponent 정책**이 됩니다 (lookahead 랜덤화만 추가).
> 버리지 말고 유지하세요. `controller/ftg`(Follow-the-Gap)는 **baseline 비교군 + 실차 fallback**.

### 4-4. Local Planning

| 겪은 문제 | 해결 |
|---|---|
| cluster→분류→tracking 방식이 **벽과 벽 구조물을 장애물로 오분류** → 급감속으로 global 경로 이탈. 파라미터를 풀면 실제 장애물을 놓침 | **centerline 추출 시 만든 wall boundary 파일을 현재 LiDAR 스캔과 매칭**해 벽/장애물 분리 |
| 시간 부족 | 회피 경로 생성 없이 **trailing만 구현** |

주요 파일: `local_planning.py`, `local_planning.yaml`, `local_planning.launch.xml`

> [!note] 이 문제가 E2E를 정당화하는 근거
> "벽인가 장애물인가"를 명시적으로 분류하려다 실패한 겁니다.
> E2E policy는 **raw LiDAR를 직접 먹고 행동을 내므로 이 분류 단계 자체가 사라집니다.**
> 프로젝트 발표·리포트에서 **E2E 채택 이유로 쓸 수 있는 가장 구체적인 근거**입니다.

## 5. TO-BE — RL E2E 스택 (TM07 아키텍처)

### 5-1. 관측 공간 — Asymmetric

| | Actor $\pi$ (실차에서 사용) | Critic $Q$ (학습 시에만) |
|---|---|---|
| 입력 | LiDAR **270-dim** + $s_{\text{ego}} = [v_x,\ \delta_{t-1},\ I_{\text{overtake}}]$ | **24-dim privileged obs** |
| history | $N = 4$ frame stacking | — |
| 내용 | 실차에서 실제로 얻을 수 있는 것만 | track coord, $e_{\text{lat}}$, $e_{\psi}$, curvature, wall distance, opponent 상대좌표 |

→ [[Asymmetric Actor-Critic (Pinto 2017)]], [[POMDP]]

### 5-2. 알고리즘

**Asymmetric SAC** — [[SAC (Haarnoja 2018)]] + [[SAC v2 (Haarnoja 2018)]](auto entropy tuning)
구현 베이스: CleanRL `sac_continuous_action.py` fork

### 5-3. 보상 설계

$$R = r_{\text{progress}} + r_{\text{safety}} + r_{\text{TTC}} + r_{\text{overtake}}$$

steering smoothness penalty (sim2real 필수):

$$B_{\text{steer}} = -\lvert \delta_t - \delta_{t-1}\rvert \cdot \left(\lambda_H + \frac{v_x}{V_{\max}}\lambda_{H,\text{speed}}\right)$$

TTC $= \text{Gap} / (v_{\text{ego}} - v_{\text{opp}})$, 페널티는 $1/\text{TTC}$

→ [[Reward Shaping]], [[Potential-based Shaping]]

### 5-4. 커리큘럼

**Two-Phase Automatic Curriculum** — Phase 1(solo) → Phase 2(추월), 전이 게이트는 **lap completion EMA > 60%**
opponent = Pure Pursuit, **lookahead 랜덤화** (20/20/60) → [[Curriculum Learning]], [[Domain Randomization]]

### 5-5. 새로 만들 코드

```
rl_racing/
├─ envs/
│   ├─ racing_env.py       # Gymnasium 래퍼 (f110_gym 위)
│   ├─ observation.py      # actor obs / critic privileged obs
│   ├─ reward.py           # r_progress + r_safety + r_TTC + r_overtake + B_steer
│   ├─ opponent.py         # Pure Pursuit opponent + lookahead randomization
│   └─ randomization.py    # friction, mass, latency, noise
├─ curriculum/manager.py   # Phase 1→2 FSM, EMA gate
├─ algo/asymmetric_sac.py  # CleanRL fork
├─ deploy/
│   ├─ export_onnx.py
│   └─ policy_node.py      # ROS 2: /scan → policy → /drive (+ low-pass filter)
└─ configs/
```

## 7. 3-Tier 학습·배포 파이프라인

| Tier | 환경 | 목적 |
|---|---|---|
| **Tier 1** | `f1tenth_gym` (SIL) | 주 학습. 빠른 반복 |
| **Tier 2** | Isaac Sim / Isaac Lab | 고충실도 검증. 실패 시 → **DR 범위 확대 후 Tier 1 재학습** |
| **Tier 3** | 실차 (Jetson) | ONNX → TensorRT, `α=0.5` 저속 완주 → 단계적 속도 상향 |

### Reality gap 원인 → 대응

| 원인 | 대응 |
|---|---|
| tire friction / 노면 | friction coefficient randomization |
| **actuator latency** (서보·ESC 지연) | latency randomization + 시뮬에 delay buffer |
| 제어 주기 지터 (Jetson 부하) | 고정 주기 실행 + 지터 randomization |
| LiDAR noise / dropout / 반사 | gaussian noise, random dropout, max-range 처리 |
| VESC 속도 추정 오차 (ERPM→m/s) | $v_x$ 관측에 noise + bias randomization |
| 배터리 전압 sag | 최대 가속·속도 스케일 randomization |
| 질량 / 무게중심 / $I_z$ | mass, CoM, $I_z$ randomization |

### 실차 배포 체크리스트

- [ ] ONNX → **TensorRT** export (PyTorch 직접 추론은 지터 큼)
- [ ] **관측 전처리를 시뮬과 비트 단위로 동일하게** — LiDAR 1080→270 downsample 방식, 각도 범위, clip, normalize 통계
- [ ] 고정 제어 주기 + 주기 위반 로깅
- [ ] **Action Low-Pass Filter** $a_t = (1-\alpha)a_{t-1} + \alpha \cdot a_{\text{model}}$, 시뮬 $\alpha{=}1.0$ → 실차 $\alpha{=}0.4\text{–}0.6$
- [ ] E-stop / watchdog (`controller/estop.py` 재사용)
- [ ] 속도 상한 램프업 ($v_{\max}$ 50%부터)
- [ ] fallback controller (`controller/ftg`)

## 8. 미확정 — 우리가 직접 정해야 하는 것

TM07 리포트에 **명시되지 않아** 재현 시 반드시 막히는 지점들입니다.

| 항목 | 상태 |
|---|---|
| **action space** | $[\delta, v]$ 인지 $[\delta, \text{throttle}]$ 인지, 절대값인지 증분인지 미명시 |
| **network 구조** | hidden dim, layer 수, LiDAR 270-dim을 1D-CNN인지 MLP인지 미명시 |
| **reward 가중치** | $\lambda_H$, $\lambda_{H,\text{speed}}$ 등 값 미공개 → 직접 튜닝 |
| **entropy temperature $\alpha$** | 자동 조정 여부 미명시 → [[SAC v2 (Haarnoja 2018)]] auto-tuning이 정석 |
| **Phase 2 gap 스케줄** | "30–50 → 5–50"은 오타로 추정 (`5–15`가 자연스러움) → 직접 설계 |
| **⚠️ 차량 파라미터** | **최대 리스크.** 1/8 Serpent vs gym 기본 1/10 F1TENTH. wheelbase, mass, $I_z$, 타이어 계수($C_{Sf}$, $C_{Sr}$), $v_{\max}$, steering limit, ESC duty↔속도 매핑을 **system identification으로 재측정** 필요 |

> [!danger] 최대 리스크
> 차량 파라미터 확보가 늦어지면 **M5~M6에서 전부 다시 학습**해야 합니다.
> M0~M1과 **병행해서** 실차 system identification(스텝 응답으로 steering 지연·게인, 가감속 프로파일, 최대 횡가속도)을 시작할 것.
> §4-2의 `friction_test.py` 측정값이 재사용 가능한지 **먼저 확인**하세요.

